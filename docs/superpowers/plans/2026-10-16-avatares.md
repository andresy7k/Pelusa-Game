# Plan: Avatares de jugador (2026-10-16)

Spec: `docs/superpowers/specs/2026-10-16-avatares-design.md`.
Mismo flujo SDD que el hero: brief → implementación → verificación → review.
Rama: `feature/avatares` desde `feature/hero-seleccion` (si el hero aún no se
mergeó). Push/PR solo con autorización explícita.

## Restricciones globales

- El servidor es la autoridad: rango + unicidad se validan en backend aunque la
  UI ya lo impida.
- V1..V5 de Flyway no se tocan; V6 hace backfill antes de NOT NULL.
- Todo el texto de UI y comentarios en español. Accesibilidad: radios nativos,
  foco visible, teclado.
- Backend se explica en modo PROFESOR (el autor lo defiende).

## Review Focus

1. Migración sobre DB existente (backfill) sin romper `FlywayMigrationTest`.
2. Condición de carrera de unicidad: aunque la UI deshabilite chips, dos
   requests simultáneos no pueden crear la misma pelusa (constraint DB).
3. Compatibilidad: requests viejos sin `avatars` siguen creando partidas.
4. a11y del picker: radiogroup navegable, labels claros, estados anunciados.

### Task 1: Backend — avatar validado en servidor (MODO PROFESOR)

**Files:**
- Create: `backend/src/main/resources/db/migration/V6__player_avatar.sql`
- Modify: `backend/src/main/java/com/pelusa/infrastructure/persistence/PlayerEntity.java`
- Modify: `backend/src/main/java/com/pelusa/infrastructure/web/dto/CreateGameRequest.java`
- Modify: `backend/src/main/java/com/pelusa/application/GameService.java` (`create`)
- Modify: `backend/src/main/java/com/pelusa/application/dto/GameView.java` (`PlayerView`)
- Modify: `backend/src/test/java/com/pelusa/GameApiTest.java`

**Steps:**
1. Migración V6 con backfill por `ROW_NUMBER` + NOT NULL + CHECK + UNIQUE.
2. `PlayerEntity` suma `avatar` (constructor + getter).
3. `CreateGameRequest` suma `List<Integer> avatars` (opcional).
4. `GameService.create(names, firstPlayerIndex, avatars)`: si viene, validar
   tamaño + rango + duplicados (→ `VALIDATION_FAILED`); si no, asignar
   `seat + 1`. Pasar el avatar al constructor de `PlayerEntity`.
5. `PlayerView(id, name, seat, avatar)`.
6. Tests de API: feliz, duplicado → 400, rango → 400, sin avatares → distintos.
7. Build local (Maven de temp + JRE17) + smoke con el jar.

**Verify:** `mvn test` verde; `POST /api/games` con/sin avatares responde
`players[].avatar` correcto; duplicado devuelve 400 `VALIDATION_FAILED`.

**Commit:** `feat(avatares): eleccion de pelusa unica por partida validada en servidor`

### Task 2: Setup — el jugador elige su pelusa

**Files:**
- Create: `frontend/src/components/monsters.ts` (colores compartidos)
- Create: `frontend/src/components/AvatarPicker.tsx` (+ css si hace falta)
- Modify: `frontend/src/routes/Setup.tsx`
- Modify: `frontend/src/api/client.ts` (`create` manda `avatars`)
- Modify: `frontend/src/api/types.ts` (`PlayerView.avatar`)

**Steps:**
1. `monsters.ts`: `MONSTER_COLORS: Record<number, string>` con los 10 hex de
   `card.css` (única fuente para piezas nuevas).
2. `AvatarPicker`: radiogroup por jugador con 10 chips (`MonsterFace` + color);
   preselección del primer libre; chips tomados deshabilitados con nombre del
   dueño; cambio en un clic.
3. `Setup`: estado `avatars[]` junto a `names[]`; validación antes de enviar;
   `api.create(names, 0, avatars)`.
4. Verificación visual con captura (puppeteer) en 2–6 jugadores; teclado.

**Verify:** tsc + build; captura del paso 2 con chips y estados
seleccionado/tomado; crear partida real y ver la mesa.

**Commit:** `feat(setup): picker de avatar por jugador, sin repetir pelusa`
